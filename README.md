# DAODecomp

A functional decompilation of **Dragon Age: Origins**. The intended result is a
replacement executable using the original game's data files. A byte-identical
whole executable is not required. Complete reccmp matches from native x86 C++
are an automatic acceptance path; nonmatching functions remain available for
iteration or other checking. Observable function behavior is the overall goal.

**[Browse the recovered native C++ and matching-function index](src/native/recovered/README.md).**
This published source snapshot tracks the new reccmp/object workflow separately
from the historical emulator-validated registry below. The recovery harness and
source snapshot currently live on the `codex/rapid-recovery` branch.

The GOG Windows installer labeled `1.05 (a) (10692)` is unpacked in `gamedata/`;
all 32,850 extracted files passed installer checksum verification. A Windows 11
ARM64 VM is available for translated reference experiments; native x86 hardware
corroboration remains unavailable. Symbolic proofs and a full game executable
loader remain planned. The synthetic example below is separate infrastructure testing.

New recovery uses an [all-function object-file loop](docs/object-recovery.md).
DeepSeek writes C++ with inline address markers and dependency declarations;
the historical x86 compiler builds individual COFF objects without linking.
Missing dependency implementations therefore do not prevent compilation.
The comparator resolves known function/global references to pinned original
addresses and accepts exact full-function matches. Unknown comparisons remain
available for iteration. C++ is the only authored per-function artifact.

All **27,555 inventory identities** are catalogued, including calls, globals,
imports, indirect calls, floating point, TLS and discontiguous or large bodies.
The initial queue imports **807 existing native matches** and schedules the other
**26,748 functions in 2,904 groups**. These counts describe the initial preparation;
live results are available through `python -m rapid_object status`. Signature
hypotheses can improve during recovery rather than blocking generation. Object
matches remain evidence for pinned compiled artifacts, not a universal proof or
a working game.

The first native pilot produced **four complete function matches**, after one
DeepSeek repair, using the VC8 x86 compiler in the Windows ARM64 VM. Its two
provider requests cost an estimated **$0.01091232**. These matches have their own
provenance and counts; they are not added to the historical registry above.
The exact [pilot C++](src/native/reccmp_pilot.cpp) is retained in the repository
and builds through the native loop, separately from the portable CMake targets.

The object runner uses **16 provider lanes** and up to six repairs per batch.
Repairs focus on unmatched functions, retain the best source, and stop after
repeated lack of progress. Large bodies use context pages; known truncated
responses can split into smaller groups while preserving consumed allowances.
The shared request ceiling is 120 per half hour and the existing $50/day DeepSeek
budget remains in force. Ledger values are conservative peak-price budget
estimates, not actual billed dollars. The earlier
[native C++ and reccmp loop](docs/reccmp-loop.md) and its results remain retained;
its exhausted call-free queue is stopped.

The earlier [lightweight candidate factory](docs/rapid-recovery.md) retains its
register-state C++ proposals but is paused for this native-ABI transition.
Syntax-only proposals do not contribute to the historical progress counts above.

The previous [recovery workflow](docs/continuous-recovery.md) and its
[queue](analysis/recovery-queue.json) remain historical records. Its suspended
checkpoint is preserved in the original checkout; the new runner does not resume
or modify that work.

## Validate the recovered functions

After building and installing the dependencies below, with the original game at
`gamedata/bin_ship/DAOrigins.exe`:

The historical [incremental checkpoint](docs/continuous-recovery.md) rebuilds
current source and reuses comparisons only when their execution inputs still
match exactly. It is not a prerequisite for new native candidates. Existing
groups can be replayed with these commands:

```sh
.venv/bin/python validation/validate_leaves.py --suite all --jobs 4
.venv/bin/python validation/validate_leaves.py --expect-mismatch
.venv/bin/python validation/validate_memory.py --suite all --jobs 3
.venv/bin/python validation/validate_memory.py --expect-mismatch
.venv/bin/python validation/validate_object_counters.py --suite all --jobs 3
.venv/bin/python validation/validate_object_counters.py --expect-mismatch
.venv/bin/python validation/validate_indexed_stores.py --suite all --jobs 2
.venv/bin/python validation/validate_indexed_stores.py --expect-mismatch
.venv/bin/python validation/validate_indexed_fields.py --execution batch --suite all --jobs 4
.venv/bin/python validation/validate_indexed_fields.py --execution batch --expect-mismatch
.venv/bin/python validation/validate_object_bitfields.py --suite all --jobs 4
.venv/bin/python validation/validate_object_bitfields.py --expect-mismatch
.venv/bin/python validation/validate_direct_object_fields.py --binary gamedata/bin_ship/DAOrigins.exe --build-dir build --report-dir reports/direct-object-fields --suite all --jobs 4 --execution batch
.venv/bin/python validation/validate_direct_object_fields.py --binary gamedata/bin_ship/DAOrigins.exe --build-dir build --report-dir reports/direct-object-fields --expect-mismatch --execution batch
.venv/bin/python validation/validate_linked_structures.py --suite all --jobs 2
.venv/bin/python validation/validate_linked_structures.py --expect-mismatch
```

The runner verifies binary/slice hashes and executes the registered arithmetic and
byte-processing functions in isolation. It checks return values, stack balance, preserved registers
and the absence of memory side effects. Each implementation runs twice per input in
fresh processes. The negative control removes the special all-bits sentinel.
See [initial function evidence](analysis/first-leaves.md), the
[low-cost model pilot](analysis/pilots/luna-001.md), the
[validation records](analysis/validation/), and
[repeatable static analysis](docs/static-analysis.md). No Windows host is needed
for these isolated checks; game initialization and scenario tests still need one.
Use `--function NAME` to select a function, `--suite heldout` for the pilot's
withheld cases, or `--report-dir PATH` to retain a separate run. Parallel validation
uses independent processes; it does not launch model workers.

The memory runner additionally checks complete 128-byte guest allocations,
normalized pointer returns, unaligned accesses, and overlapping source/destination
ranges. Reads and writes outside the declared footprint fail. Its negative control
uses an intentionally wrong snapshot copy that loses sequential overlap effects.
See the [memory recovery record](analysis/memory-001.md).

The object-counter adapter uses separate 512-byte allocations and checks exact
field footprints, wraparound and sentinel return values. See the
[object-counter recovery record](analysis/object-counters-001.md).

The indexed-store adapter checks conditional byte/word writes, truncation, all
incoming EAX bits on rejected indexes, and preserved ECX in the original slice.
Its negative control incorrectly clears the upper return bits on rejected indexes.
See the [indexed-store recovery record](analysis/indexed-stores-001.md).

Eleven related indexed getters and setters additionally preserve narrow reads,
full incoming return bits and distinct rejected-index sentinels. See the
[indexed-field recovery record](analysis/indexed-fields-002.md).

Fifteen related object functions cover flag updates, packed fields, color merging,
sequential overlapping copies and conditional pointer traversal. Their observations
include full return/register bits and every arena byte. See the
[object-bitfield recovery record](analysis/object-bitfields-001.md).

Twenty-two direct object-field helpers preserve narrow return bits, exact writes,
field predicates and raw exit ECX. See the
[direct-field recovery record](analysis/direct-object-fields-001.md).

The linked-structure adapter validates disjoint list/node graphs, raw guest
pointers (including a valid node at arena offset zero), exact branch footprints
and every arena byte. Its three controls corrupt append's return, pop's retained
link, and unlink's observed ECX. See the
[linked-structure evidence](analysis/linked-structures-001.md) and
[unlink evidence](analysis/linked-unlink-001.md).

## Run the demonstration

Requirements: Python 3.10+, CMake 3.20+, a C++20 compiler. The core tooling uses the
Python standard library; the x86 demonstration additionally uses pinned Unicorn.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-validation.txt
cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure
.venv/bin/python examples/synthetic/demo.py
.venv/bin/python examples/synthetic/demo.py --expect-mismatch
```

On Windows use `.venv\Scripts\python.exe`; for Visual Studio builds add
`--config RelWithDebInfo` to the build, `-C RelWithDebInfo` to CTest, and
`--build-dir build/RelWithDebInfo` to both demo invocations.

The demo executes actual 32-bit x86 instructions in Unicorn and a separately
compiled native C++ function. It compares the return value and both fields of a
mutable counter across 59 deterministic cases, twice per implementation in fresh
processes. The intentionally broken version treats an exact maximum as overflow;
the second command succeeds only when a semantic mismatch is detected without
runner errors. JSON reports and replayable cases appear in `reports/`.

## Automatic progress updates

Enable the versioned pre-commit hook once per clone:

```sh
git config --local core.hooksPath .githooks
```

Every commit refreshes and stages only the generated progress block above, using
the **staged** function registry, static inventory and validation records. Unstaged
source changes and unrelated README edits stay outside the commit. The hook needs
Python 3.10+ and Git; it does not need the game install or validation dependencies.

To refresh manually or check without changing files:

```sh
python3 tools/update_progress.py
python3 tools/update_progress.py --check
```

CI checks the committed version with `--staged --check`, including on clones where
the hook has not been enabled. Add recovered functions to `analysis/functions.json`
and save validation records under `analysis/validation/`; the counts follow those
records automatically. Passing evidence is counted only while all recorded tracked
inputs match. Changing those inputs, including the registry, conservatively removes
the old evidence from the current count until refreshed results are recorded.

## Fingerprint the original

For the extracted reference executable:

```sh
python3 -m tools.daodecomp fingerprint gamedata/bin_ship/DAOrigins.exe --output local/manifests/DAOrigins.exe.json
```

This reads the PE headers and SHA-256 without executing or modifying the file.
Build hashes identify the reference; they are not binary-matching targets. Keep
original binaries/assets/captures outside tracked source. No game data is bundled.
